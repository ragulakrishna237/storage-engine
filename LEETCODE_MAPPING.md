# LeetCode ↔ storage-engine mapping

This table maps mechanisms that the engines actually implement to LeetCode
problems that exercise the same *idea*. The mapping is pedagogical: passing
the LeetCode problem is not the same as implementing InnoDB, PostgreSQL, or
Redis, and this repo does not reimplement those internals.

The runnable demos (`examples/`) exercise the mechanism against a real
container. See [docs/innodb.md](docs/innodb.md), [docs/postgresql.md](docs/postgresql.md),
and [docs/redis.md](docs/redis.md) for the walkthroughs.

| Mechanism | LeetCode problem | How the demo exercises it |
|---|---|---|
| B+ tree search (clustered PK, secondary key) | [704 Binary Search](https://leetcode.com/problems/binary-search/) | `SELECT * FROM users WHERE user_id = 1` descends the InnoDB clustered B+ tree (and the PostgreSQL btree) by comparing keys at each page, the same ordered-search idea as binary search on a sorted array. Internal pages store separator keys; leaf pages store records. |
| Range scan | Range-query / sliding-window family (e.g. [209 Minimum Size Subarray Sum](https://leetcode.com/problems/minimum-size-subarray-sum/), [239 Sliding Window Maximum](https://leetcode.com/problems/sliding-window-maximum/)) | `score BETWEEN 50 AND 60` / `ZRANGEBYSCORE 50 60` walks a contiguous key interval. That is a range scan, not “sliding window” as a problem statement, but the same *walk a sorted interval* pattern. |
| Buffer pool midpoint LRU | [146 LRU Cache](https://leetcode.com/problems/lru-cache/) | InnoDB’s buffer pool is an LRU of 16 KiB pages. Unlike textbook LRU, new pages enter at the **midpoint** (`innodb_old_blocks_pct`, default 37%) and are promoted to the “young” half only after a second access past `innodb_old_blocks_time`. The 10k-row insert and the range scan pull pages into that pool; this repo does not print pool internals. |
| Hash table | [1 Two Sum](https://leetcode.com/problems/two-sum/) / [706 Design HashMap](https://leetcode.com/problems/design-hashmap/) | Redis’s dict is the keyspace and the member→score map inside a zset. `ZSCORE` is an O(1) dict lookup. InnoDB’s adaptive hash index is also a hash table, built in memory over hot B+ tree leaf records for repeated point lookups. |
| Skip list | [1206 Design Skiplist](https://leetcode.com/problems/design-skiplist/) | Redis zset (once past listpack size) stores members in a skip list ordered by `(score, member)`. `ZADD` inserts, `ZRANGEBYSCORE` walks, `ZREM` deletes. 10k members uses the skiplist+dict encoding, not listpack. |
| WAL sequential append | **No perfect LeetCode analog** | Redo/WAL is “append a log record, then later flush the page.” Array/string append problems are a weak metaphor (amortized append, not durability). The demos issue INSERT/UPDATE/DELETE, which generate WAL on InnoDB and PostgreSQL; they do not dump `ib_logfile` or `pg_wal`. Treat this row as “there isn’t a clean LC problem for write-ahead logging.” |
| MVCC version chains | [206 Reverse Linked List](https://leetcode.com/problems/reverse-linked-list/) / [141 Linked List Cycle](https://leetcode.com/problems/linked-list-cycle/) — **analogy, not identity** | InnoDB clustered records hold `trx_id` + `roll_ptr`. A consistent read that cannot see the current `trx_id` follows `roll_ptr` through undo records until it finds a visible version — a pointer chase, like walking a linked list. It is not LC 206/141: undo is a log, not a list you reverse, and visibility uses a Read View, not “has cycle.” PostgreSQL instead leaves prior heap tuples in place (`xmin`/`xmax`) rather than an undo chain. |
| Heap HOT update | In-place vs copy-on-write (conceptual; no single LC problem) | PostgreSQL **HOT** (Heap-Only Tuple): if the UPDATE does not change any indexed column *and* the new tuple fits on the same heap page, Postgres writes the new version on that page and leaves indexes pointing at the old line pointer. That is closer to in-place versioning than to a full copy-on-write of every index. Updating `score` (indexed) is **not** HOT; updating only `updated_at` **is** the HOT-friendly case in `examples/postgres_demo.sql`. |
| Adaptive hash index | [1 Two Sum](https://leetcode.com/problems/two-sum/) / [706 Design HashMap](https://leetcode.com/problems/design-hashmap/) | Repeated `WHERE user_id = ?` lookups against InnoDB may be satisfied from the AHI instead of walking the B+ tree. The demo issues a PK lookup; whether AHI is used depends on `innodb_adaptive_hash_index` and access frequency. Do not treat a single EXPLAIN as proof AHI fired. |
| Change buffer | Deferred work / write combining (no clean LC analog) | InnoDB can buffer secondary-index updates for pages that are not in the buffer pool and merge them later. The score index is non-unique, so inserts of `(score, user_id)` are eligible. Clustered PK inserts are never change-buffered. |
| B-link tree (PostgreSQL btree) | [704 Binary Search](https://leetcode.com/problems/binary-search/) plus a concurrency footnote | PostgreSQL btree pages have a right-link (Lehman & Yao). A descent that races a page split can follow the right-link instead of restarting from the root. The demo’s PK lookup and score range scan walk that btree; they do not induce splits on demand. |
| VACUUM / dead-tuple reclamation | No perfect LC analog (memory allocators / garbage collection are the usual comparison) | `DELETE FROM users WHERE user_id = 2` sets `xmax`; the index entry remains until `VACUUM`. The demo runs `VACUUM (VERBOSE, ANALYZE)` and then reads `n_dead_tup` from `pg_stat_user_tables`. |
